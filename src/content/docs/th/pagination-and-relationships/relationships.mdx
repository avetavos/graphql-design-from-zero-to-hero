ในฐานข้อมูลเชิงสัมพันธ์ คุณแสดงการเชื่อมโยงด้วย foreign key และ join table ส่วนใน GraphQL การเชื่อมโยง *เดียวกัน* ตรงไปตรงมากว่ามาก คือ relationship เป็นเพียง **field ที่มี type เป็น type อีกตัว** ไม่มี syntax พิเศษ ระบบ type ที่คุณรู้อยู่แล้วเพียงพอ

สิ่งที่เปลี่ยนไปจาก relationship หนึ่งสู่อีกอันมีเพียง **รูปร่าง** ของ field คือค่าเดี่ยว, list หรือ list บนทั้งสองฝั่ง

## One-to-one และ one-to-many

การเชื่อมโยงที่ง่ายที่สุดคืนค่าเป็น object เดี่ยว `Post` หนึ่งอันเป็นของ `Author` คนเดียวเท่านั้น type ของ field จึงเป็นแค่ `Author`:

```graphql
type Post {
  id: ID!
  title: String!
  author: Author!
}
```

ทิศทางย้อนกลับเป็นแบบ **one-to-many**: author หนึ่งคนมี post หลายอัน type ของ field จึงกลายเป็น list คือ `[Post!]!`:

```graphql
type Author {
  id: ID!
  name: String!
  posts: [Post!]!
}
```

นั่นคือรูปแบบทั้งหมด ฝั่ง "to-one" คืนค่าเป็น type ส่วนฝั่ง "to-many" คืนค่าเป็น list ของ type นั้น และ type คู่เดียวกันเปิดเผย relationship ได้จากทั้งสองปลาย ทำให้ client เดินได้ทั้งสองทิศทาง

## Many-to-many

เมื่อทั้งสองฝั่งมีอีกฝั่งได้หลายอัน คุณจะได้ relationship แบบ **many-to-many** เช่น `Post` หนึ่งอันถือ `Tag` หลายอัน และแต่ละ `Tag` ก็ติดอยู่กับ post หลายอัน ใน SDL คือ field ที่เป็น list บน type *แต่ละตัว*:

```graphql
type Post {
  id: ID!
  title: String!
  tags: [Tag!]!
}

type Tag {
  id: ID!
  label: String!
  posts: [Post!]!
}
```

ไม่มี "join table" โผล่ใน schema — งานเบื้องหลังอยู่ใน data layer ของคุณ ส่วน client เห็นเพียง type สองตัว แต่ละตัวมี field ที่เป็น list ชี้ไปยังอีกตัว

## การ resolve อีกฝั่งหนึ่ง

การประกาศ field เป็นเพียงครึ่งหนึ่งของงาน อีกครึ่งคือ **resolver** ที่ดึงข้อมูลอีกฝั่งมาให้ตอน client เลือก field นั้นจริง ๆ

resolver ของ field ที่เป็น relationship จะได้รับ object *parent* มา แล้วใช้ id ของ parent ค้นหา record ที่เชื่อมต่ออยู่ และเพราะ GraphQL รัน resolver ต่อเมื่อมีคนขอ field นั้น ดังนั้นถ้า client ขอ `name` แต่ไม่ขอ `posts` ก็ไม่เสียต้นทุนโหลด post เลย

## การข้าม relationship รันจริง

schema ด้านล่างเชื่อม one-to-many (`Author` → `posts`) เข้ากับ many-to-many (`Post` ↔ `Tag`) พร้อม resolver ที่ค้นหาอีกฝั่งด้วย id ตัว query ข้ามสาม relationship ในหนึ่ง request กดปุ่ม **Run**

export const relCode = `(async () => {
  const { graphql, buildSchema } = await import('https://esm.sh/graphql@16');

  const schema = buildSchema(\`
    type Author {
      id: ID!
      name: String!
      posts: [Post!]!
    }

    type Tag {
      id: ID!
      label: String!
      posts: [Post!]!
    }

    type Post {
      id: ID!
      title: String!
      author: Author!
      tags: [Tag!]!
    }

    type Query {
      author(id: ID!): Author
    }
  \`);

  // Plain tables, the way a data layer would store them.
  const authors = { a1: { id: 'a1', name: 'Ada Lin' } };
  const tags = {
    t1: { id: 't1', label: 'design' },
    t2: { id: 't2', label: 'graphql' },
  };
  const posts = [
    { id: 'p1', title: 'Designing a graph', authorId: 'a1', tagIds: ['t1', 't2'] },
    { id: 'p2', title: 'Walking relationships', authorId: 'a1', tagIds: ['t2'] },
  ];

  // Build a Post object whose relationship fields resolve the other side.
  const buildPost = (p) => ({
    id: p.id,
    title: p.title,
    author: () => buildAuthor(authors[p.authorId]),
    tags: () => p.tagIds.map((id) => buildTag(tags[id])),
  });

  const buildTag = (t) => ({
    id: t.id,
    label: t.label,
    posts: () => posts.filter((p) => p.tagIds.includes(t.id)).map(buildPost),
  });

  const buildAuthor = (a) => ({
    id: a.id,
    name: a.name,
    // One-to-many: find every post whose authorId matches.
    posts: () => posts.filter((p) => p.authorId === a.id).map(buildPost),
  });

  const root = {
    author: ({ id }) => (authors[id] ? buildAuthor(authors[id]) : null),
  };

  const query = \`
    {
      author(id: "a1") {
        name
        posts {
          title
          tags { label }
        }
      }
    }
  \`;

  const result = await graphql({ schema, source: query, rootValue: root });
  console.log(JSON.stringify(result, null, 2));
})();`;

ไล่ดูผลลัพธ์: จาก `author` หนึ่งคน เรา resolve `posts` แบบ one-to-many และภายในแต่ละ post เรา resolve `tags` แบบ many-to-many

ทุก field ที่เป็น relationship มี resolver ของตัวเองที่ค้นหา record ปลายทางด้วย id สังเกตว่าเราไม่เคยเขียน SQL `JOIN` เลย — กราฟ *คือ* การ join ที่แสดงออกผ่านการเลือก field แบบซ้อนกัน

| ข้อดี | ข้อแลกเปลี่ยน |
|---|---|
| query relationship ได้ในครั้งเดียว — ไม่ต้อง join ที่ client | deep relationship นำไปสู่ N+1 ถ้าไม่ใช้ DataLoader |
| schema แสดง relationship ชัดเจน — เข้าใจ data model ได้จาก schema | circular relationship อาจ query วนซ้ำไม่รู้จบ |
| lazy load — query เฉพาะ relationship ที่ต้องการ | bidirectional relationship ต้องระวัง infinite loop ใน resolver |
| resolver แต่ละ field ทำงาน independent | relationship ที่ไม่มี DataLoader อาจทำให้ query ช้ามาก |

## ข้อผิดพลาดที่พบบ่อย

**Circular Relationship ที่ไม่มี Depth Limit**
อาการ:
- `User.posts.author.posts.author.posts...` — query วนซ้ำได้ไม่จำกัด
- malicious client ส่ง deeply nested query ทำให้ server overload
- ต้องมี query depth limit (Rule: depth-and-complexity)

**Relationship ที่ Return ทั้ง Collection โดยไม่มี Pagination**
อาการ:
- `user { posts { title } }` — return โพสท์ทั้งหมดของ user
- user ที่มีโพสท์หมื่นชิ้น ทำให้ query ช้ามาก
- relationship collection ควรมี pagination argument เสมอ: `posts(first: 10)`

> 💡 ตัวอย่างจากของจริง
>
> **GitHub:**
> - relationship collection ใช้ Relay Connection spec ทุกจุด: `user { repositories(first: 20) { ... } }` ([GitHub GraphQL pagination guide](https://docs.github.com/en/graphql/guides/using-pagination-in-the-graphql-api))
> - ไม่มี relationship ที่ return unbounded list
>
> **Prisma:**
> - ORM ที่ใช้คู่กับ GraphQL บ่อย — relationship query ทำผ่าน `include` และ `select` ([Prisma relation queries docs](https://www.prisma.io/docs/orm/prisma-client/queries/relation-queries))
> - มักใช้ร่วมกับ DataLoader ใน resolver เพื่อป้องกัน N+1

<Callout title="relationship ก็คือ field ที่มี type นั่นเอง">
ไม่มีแนวคิด "relationship" แยกต่างหากให้เรียนใน GraphQL — การเชื่อมโยงคือ field ที่มี type เป็น type อีกตัว (to-one) หรือ list ของ type อีกตัว (to-many) ส่วน many-to-many ก็เป็นเพียง field ที่เป็น list บนทั้งสองปลาย

สร้างโมเดลเฉพาะทิศทางที่ client ของคุณเดินผ่านจริง ๆ ใส่ resolver ให้ทุก field ที่เป็น relationship เพื่อดึงอีกฝั่ง แล้วระบบ type จะเปลี่ยนข้อมูลของคุณเป็นกราฟให้เอง
</Callout>
