ใน[บทเรียนก่อนหน้า](/graphql/th/errors-and-validation/) เราเห็นแล้วว่า response พก `errors` array มาด้วยได้ คราวนี้มาแกะ array นั้นกัน ทุก entry คือ object ที่มีชุด key ตายตัว พออ่าน key พวกนี้เป็น คำว่า "มีอะไรพังสักอย่าง" ที่คลุมเครือจะกลายเป็น "field นี้ ตรงตำแหน่งนี้ใน query ของคุณ พังเพราะเหตุนี้"

## กายวิภาคของ error entry

แต่ละ element ใน `errors` มี key บังคับหนึ่งตัว และ key ที่จะใส่หรือไม่ใส่ก็ได้อีกหลายตัวตามที่ spec กำหนด

- `message` — string ที่คนอ่านรู้เรื่อง อธิบายว่าพังเพราะอะไร นี่คือ key เดียวที่บังคับ
- `locations` — รายการตำแหน่ง `{ line, column }` ชี้ไปยังจุดที่แน่นอนใน**ตัว query text** ที่ทำให้เกิด error
- `path` — รายการชื่อ field และ index ของ list ไล่จาก root ของ response ลงไปถึง field ที่พัง เช่น `["currentTrack", "title"]`
- `extensions` — map ไว้ใส่รายละเอียดแบบเครื่องอ่านได้ และมีบทเรียนถัดไปทั้งบทให้เรื่องนี้

ค่า `message` มีไว้ให้คนอ่าน ส่วน `locations` กับ `path` มีไว้ให้ tooling และ client ที่ต้องเขียนโค้ดตอบสนอง สองตัวนี้รวมกันทำให้ client ไฮไลต์ส่วนที่มีปัญหาใน query และโยนความล้มเหลวไปแสดงถูกที่ใน UI ได้

## error สองตระกูล

error ไม่ได้เกิดในขั้นตอนเดียวกันทั้งหมด ตัว spec จึงแบ่งเป็นสองตระกูล ความต่างนี้สำคัญ เพราะเป็นตัวตัดสินว่าคุณจะได้ `data` กลับมาหรือไม่ได้เลย

<Mermaid title="Request errors หยุดก่อนการ execute ส่วน field errors เกิดขึ้นระหว่างการ execute" code={errorFamilies} />

**Request errors** เกิด *ก่อน* execute จะเริ่ม คือ query parse ไม่ผ่าน หรือ parse ผ่านแต่ validate กับ schema ไม่ผ่าน เช่น เจอ field ที่ไม่รู้จัก argument ผิด type หรือ selection ผิดรูป เพราะ execute ไม่ได้เริ่มเลย response จึง**ไม่มี `data` key** (แม้แต่ `null` ก็ไม่มี) เหลือแค่ `errors` เท่านั้น

**Field errors** (หรือ execution errors) เกิด *ระหว่าง* execute ตอนที่ resolver throw หรือคืนค่าที่ไม่ถูกต้อง จังหวะนั้น server กำลังประกอบ `data` อยู่แล้ว response จึงมี `data` ติดมาด้วย โดย field ที่พังกลายเป็น `null` และมี `errors` entry ของ field นั้นแนบมา นี่คือกรณีสำเร็จบางส่วนที่เราจะเจาะลึกในบทเรียนถัดไป

## ดู request error เทียบกับ field error

ตัว runner ด้านล่างรัน operation สองอันกับ schema เดียวกัน อันแรกขอ field ที่ไม่มีอยู่จริง จึง**ตกตั้งแต่ validation** กลายเป็น request error ที่ไม่มี `data` อันที่สองรัน query ที่ถูกต้อง แต่ resolver throw จึงเป็น **field error** — `data` กลับมาโดย field ที่พังเป็น `null` ลองเทียบ output สองก้อนนี้ดู

export const errorsCode = `(async () => {
  const { graphql, buildSchema } = await import('https://esm.sh/graphql@16');

  const schema = buildSchema(\`
    type Query {
      nowPlaying: String
    }
  \`);

  const root = {
    nowPlaying: () => {
      throw new Error('player offline');
    },
  };

  // 1) Request error: "ghostField" is not on Query, so validation fails
  //    BEFORE execution. Expect errors only, and NO data key.
  const invalid = \`
    {
      ghostField
    }
  \`;
  const requestError = await graphql({ schema, source: invalid, rootValue: root });

  // 2) Field error: the query is valid, but the resolver throws DURING
  //    execution. Expect data present with the field nulled, plus errors.
  const valid = \`
    {
      nowPlaying
    }
  \`;
  const fieldError = await graphql({ schema, source: valid, rootValue: root });

  console.log('--- request error (no data key) ---');
  console.log(JSON.stringify(requestError, null, 2));
  console.log('--- field error (data present, field null) ---');
  console.log(JSON.stringify(fieldError, null, 2));
})();`;

<NodeRunner client:visible code={errorsCode} />

ดู block แรกก่อน ไม่มี `data` key มีแค่ `errors` และ entry นั้นพก `locations` ชี้ไปตรงจุดที่ `ghostField` โผล่ใน query ทีนี้ดู block ที่สอง คราวนี้ `data` มีอยู่ โดย `nowPlaying` เป็น `null` และ error ที่คู่กันพก `path` เป็น `["nowPlaying"]` ให้ client รู้แน่ชัดว่า field ไหนหายไป เป็น `errors` array ตัวเดียวกันแท้ ๆ แต่คนละสถานการณ์ และตัวแยกคือมี `data` อยู่หรือเปล่า

| ข้อดี | ข้อแลกเปลี่ยน |
|---|---|
| error array ใน response — partial success เป็นไปได้ | error และ data ผสมกันใน response เดียว — client ต้องจัดการทั้งคู่ |
| `extensions` field ให้ metadata เพิ่ม เช่น error code | developer มักลืม check `errors` array ทำให้ bug ซ่อน |
| schema validation error ชัดเจน — field ไหน type ไหนผิด | HTTP 200 เสมอแม้มี error — monitoring ที่ดู HTTP status อาจไม่รู้ |
| path ใน error บอกว่า field ไหนใน query ที่เกิด error | error format ต่างกันระหว่าง library — ต้อง normalize |

## ข้อผิดพลาดที่พบบ่อย

**Throw Generic Error ทุกอย่าง**

อาการ:
- `throw new Error("Something went wrong")` ใน resolver ทุกจุดที่ error
- client ไม่รู้ว่าเกิดอะไรขึ้น — ไม่มี error code หรือ detail
- ใช้ error class ที่ specific: `UserNotFoundError`, `ValidationError` พร้อม code ใน extensions

**ไม่ Check `errors` Array ใน Client**

อาการ:
- client check แค่ว่า `data` มีค่าหรือไม่
- request สำเร็จบางส่วนแต่ client แสดงผลราวกับสำเร็จทั้งหมด
- check `errors` array เสมอ แม้ `data` จะมีค่า

> 💡 ตัวอย่างจากของจริง
>
> **Apollo Server (เวอร์ชันปัจจุบัน v4 ขึ้นไป):**
> - built-in error class เดิม `AuthenticationError`, `ForbiddenError`, `UserInputError` ถูกถอดออกแล้ว — ให้ throw `GraphQLError` พร้อม `extensions.code` แทน ([migration guide](https://github.com/apollographql/apollo-server/blob/main/docs/source/migration-from-v3.mdx))
>
> **GitHub:**
> - error ใน response มี `message`, `type`, `path` ครบ ([ตัวอย่าง response จริง](https://github.com/orgs/community/discussions/24737))
> - client รู้ว่า field ไหนใน query ที่ fail และเหตุผลคืออะไร

<Callout title="200 ก็ยังพก errors มาได้">
HTTP status ของ GraphQL response เป็นเรื่องของ transport ไม่ใช่ของตัว operation ถ้า operation ผ่าน parse, validate แล้วเริ่ม execute ปกติจะได้ HTTP `200` กลับมา ต่อให้ field ครึ่งหนึ่ง throw ก็ตาม อย่าอ่าน `200` ว่า "ทุกอย่างเรียบร้อย" เด็ดขาด ความจริงอยู่ใน `errors` array และอยู่ที่ว่ามี `data` หรือไม่ ให้อ่านสองอย่างนั้น ไม่ใช่บรรทัด status
</Callout>
